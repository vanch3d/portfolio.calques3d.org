# i18n Rules — next-intl

All user-facing strings must be externalised to `messages/en.json`. No hardcoded
UI copy anywhere in components or pages. See ADR 006 for decisions and rationale.

---

## The hard rule

**Every string visible to the user must come from `messages/en.json` via `getTranslations()` or `useTranslations()`.**

This includes: headings, labels, button text, aria-labels, link text, empty states,
error messages, pluralised counts. It excludes: data-driven content from JSON/MDX
(position titles, project names, publication titles — these are content, not UI copy).

---

## API by context

| Context | Function | Import |
|---|---|---|
| Async Server Component (page/layout) | `getTranslations(namespace)` | `next-intl/server` |
| Client Component | `useTranslations(namespace)` | `next-intl` |

**Each component owns its own namespace.** A component calls `getTranslations()` or
`useTranslations()` directly — it does not receive strings as props from a parent.
This keeps the component encapsulated and independently testable.

---

## Component pattern

```tsx
// Server Component
import { getTranslations } from "next-intl/server";

export async function ColorSwatch({ token }: { token: string }) {
  const t = await getTranslations("LabDesignSystemColors");
  return (
    <figure aria-label={t("swatch_label", { token })}>
      <div style={{ backgroundColor: `var(--${token})` }} />
      <figcaption>{t(`${token}_name`)}</figcaption>
    </figure>
  );
}

// Client Component
"use client";
import { useTranslations } from "next-intl";

export function ThemeToggle() {
  const t = useTranslations("Nav");
  return <button aria-label={t("toggle_theme")}>{t("theme")}</button>;
}
```

## Cypress CT pattern

`cy.mountAccessible()` wraps the component in `NextIntlClientProvider` with the
full `messages/en.json`. No additional setup needed — components that call
`useTranslations()` work in CT out of the box.

```tsx
// CT spec — component calls useTranslations() internally
it("renders the swatch label", () => {
  cy.mountAccessible(<ColorSwatch token="color-ground" />);
  cy.get("figcaption").should("contain.text", "Draughting Paper");
  cy.checkA11y();
});
```

For Server Components (which call `getTranslations()`) in CT: render the resolved
output as a Client Component in the spec, or test via E2E instead.

## Namespace conventions

- Top-level key = page or domain name: `ResearchPage`, `Publications`, `CVPage`, `HomePage`
- Component-level namespaces when a component has its own strings: `ColorSwatch`, `SiteNav`
- Message keys: `snake_case`
- ICU interpolation for dynamic values: `"funded_by": "Funded by {funder}"`
- ICU plurals for counts: `"positions_count": "{count, plural, =0 {...} =1 {...} other {...}}"`
- Do not share keys across namespaces — if two components need the same string, duplicate it

---

## Adding a new string

1. Add to `messages/en.json` under the component's own namespace (create it if missing)
2. Call `useTranslations("ComponentNamespace")` or `getTranslations("ComponentNamespace")` in the component
3. TypeScript will catch missing keys via the generated types — fix before committing

---

## Adding a new locale (when needed)

1. Create `messages/<locale>.json` with all keys from `en.json` translated
2. Update `src/i18n/request.ts` to accept the new locale
3. Add `[locale]` routing segment to `app/` (see Next.js i18n routing docs)
4. Update `src/types/i18n.d.ts` if needed
