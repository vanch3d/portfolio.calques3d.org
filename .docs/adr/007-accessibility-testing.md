# ADR 007 — Accessibility Testing — axe-core in CI pipeline

**Date:** 2026-08-04
**Status:** Decided

## Context

Accessibility is a hard requirement for any public portfolio site. The site must
comply with WCAG 2.1 AA as a baseline. Manual accessibility audits are not
sufficient — violations are caught too late and regress silently.

The testing pipeline (ADR 002) already has three browser-facing layers: Cypress CT,
Cypress E2E, and Playwright. Axe-core integrations exist for all three.

The site uses Next.js App Router with Server Components. The question is whether
accessibility testing requires special handling for SSR output.

## Decision

Integrate **axe-core (open-source, Deque)** at all three browser test layers.
Target standard: **WCAG 2.1 AA**.

### Tooling

| Layer | Package | API |
|---|---|---|
| Cypress CT | `cypress-axe` | `cy.injectAxe()` + `cy.checkA11y()` |
| Cypress E2E | `cypress-axe` | `cy.injectAxe()` + `cy.checkA11y()` |
| Playwright | `@axe-core/playwright` | `new AxeBuilder({ page }).withTags([...]).analyze()` |

`cypress-axe` also provides `cy.configureAxe()` for rule-level configuration when
exceptions are documented and justified.

A `cy.mountAccessible()` custom command (defined in `cypress/support/commands.ts`)
wraps `cy.mount()` + `cy.injectAxe()` for CT specs.

### Next.js App Router — no special handling needed

axe-core analyses the DOM in the browser, not the server-rendered source. Whether
HTML is generated by a Server Component, Client Component, or static export, the
final DOM is identical from axe's perspective. No middleware, no server-side axe
runner, no special wiring required.

For CT: the Cypress iframe renders the component and axe runs against that.
For E2E: axe runs after `cy.visit()` — the page is fully hydrated by that point.
For Playwright: axe runs against the live page on Vercel preview.

### Scope per test layer

- **CT**: every component spec must check axe on the default state and key variants.
- **E2E**: every page spec must call `cy.injectAxe()` in `beforeEach` and include
  a dedicated `it("has no axe accessibility violations")`.
- **Playwright**: every page tested must include a dedicated axe test with `withTags`.

### Commercial edition (Deque axe DevTools)

Not adopted. The open-source edition covers WCAG 2.1 AA. The commercial edition
adds best-practice rules, NeedReview items, and experimental checks — useful for
deeper audits but not required for CI enforcement. Revisit if compliance requirements
tighten (e.g. EN 301 549, Section 508).

## Consequences

**Positive:**
- WCAG 2.1 AA compliance enforced automatically on every push
- Regressions caught immediately in the layer closest to the code (CT first, then E2E)
- Playwright catches post-deploy accessibility issues from the live rendered output
- No custom axe runner or server-side setup — plain DOM analysis covers SSR/SSG/ISR

**Negative / Trade-offs:**
- axe cannot catch all accessibility issues (colour contrast needs visual review,
  keyboard navigation patterns need manual testing)
- CT axe checks on unstyled components will not flag colour contrast violations
  until Tailwind design is applied (Stage 10)
- `cy.checkA11y()` halts on first violation — may need `cy.checkA11y(null, null, logViolations)`
  callback during development to see all issues at once
