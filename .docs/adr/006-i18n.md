# ADR 006 — Internationalisation — next-intl, English-only, no locale routing

**Date:** 2026-08-04
**Status:** Decided

## Context

The portfolio is English-only today. However, externalising all user-facing strings:
- makes the codebase internationalisation-ready without speculative routing
- enforces a consistent pattern for UI copy (no scattered literals)
- enables pluralisation and ICU formatting with no future cost

The site uses Next.js App Router. Any i18n library must support Server Components,
Client Components, and SSG/ISR without breaking the rendering model.

## Decision

Use **[next-intl](https://next-intl.dev)** with a single `en` locale and no
URL-based locale routing (no `[locale]` segment in `app/`).

### Why next-intl over alternatives

| Option | Reason not chosen |
|---|---|
| **next-i18next v16** | Valid App Router option (v16+ supports both App and Pages Router via `getT()` / `useT()`). Not chosen because next-intl has deeper App Router integration, better type-safety, and built-in ICU. Would have been the choice for compatibility with existing i18next ecosystems. |
| **Native Next.js dictionaries** | Documented in Next.js 16 docs. No dependency, but no ICU, no pluralisation, no type-safety. Too limited once any formatting is needed. |
| **next-international** | Smaller community, less mature App Router support. |
| **react-i18next (direct)** | Requires more boilerplate to wire into App Router server-side. |

### Why next-intl

- **ICU message syntax** — pluralisation, interpolation, date/number formatting
- **Type-safe message keys** — global `IntlMessages` type augmentation catches typos at compile time
- **App Router native** — `getTranslations()` for Server Components, `useTranslations()` for Client Components, no workarounds
- **`NextIntlClientProvider`** — transparent bridge between server and client message context
- **Actively maintained**, recommended in Next.js 16 official docs

### Locale and routing

Single locale (`en`) with no URL-based locale routing. The site URL structure
stays clean (`/research`, `/cv`) — no `/en/research` prefix.

Adding a second locale when needed:
1. Add `messages/<locale>.json`
2. Add `[locale]` segment to `app/` and update `src/i18n/request.ts`
3. Add middleware/proxy for locale detection and redirect

### Sub-component pattern

Server Component pages call `getTranslations()` and resolve all needed strings.
These are passed to sub-components as a typed `labels` prop object:

```tsx
// Page:
const t = await getTranslations("ResearchPage");
const cardLabels = {
  fundedBy: (funder: string) => t("funded_by", { funder }),
  ongoing: t("ongoing"),
};
<ProjectCard project={project} labels={cardLabels} />

// Component:
export interface ProjectCardLabels {
  fundedBy: (funder: string) => string;
  ongoing: string;
}
export function ProjectCard({ project, labels }: { project: ResearchProject; labels: ProjectCardLabels }) { ... }
```

**Why:** Sub-components are synchronous Server Components (no `async`). This keeps
them usable in Cypress Component Testing, which does not support async Server Components.
The `labels` prop also makes CT tests independent of the translation file — tests
control the exact strings and aren't broken by copy changes.

Client Components use `useTranslations()` directly (no labels prop needed).

### Message key conventions

- File: `messages/en.json`
- Top-level keys are namespace names matching the page or component (`ResearchPage`, `Publications`, `CVPage`)
- Key names: `snake_case`
- ICU interpolation for dynamic values: `"funded_by": "Funded by {funder}"`
- ICU plural: `"positions_count": "{count, plural, =0 {No positions} =1 {1 position} other {# positions}}"`

## Consequences

**Positive:**
- Zero hardcoded user-facing strings in components
- ICU pluralisation and formatting available from day one
- Type-safe message keys — compile-time catch of key typos
- Clean upgrade path to multi-locale with minimal restructuring
- CT tests are isolated from translation file (labels-as-props pattern)

**Negative / Trade-offs:**
- `labels` prop adds a parameter to every presentational sub-component
- Pages must resolve and pass all sub-component strings — coupling between page and component string needs
- Adding a string requires editing both `en.json` and the component's `Labels` interface
